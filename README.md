# Food Order Service

Учебный Go backend для заказа еды и интеграции с заведениями. Сервис хранит меню и остатки, рассчитывает стоимость заказа, резервирует товары и передаёт события отдельному demo-сервису ресторана. Проект не обслуживает реальных пользователей.

## Стек

Go 1.24, chi, PostgreSQL 16, pgx/database/sql, REST/JSON, OpenAPI, Docker Compose, GitHub Actions. Для конкурентных задач используются goroutines, context, channels, sync и atomic.

## Архитектура

- `kitchen`: HTTP API, бизнес-правила, PostgreSQL repository и фоновый outbox dispatcher.
- `postgres`: меню, остатки, заказы, история статусов и очередь событий.
- `demo-restaurant`: отдельный HTTP-сервис, который синхронизирует меню, принимает события и имитирует обработку заказа. Состояние demo хранится в памяти.
- `migrate`: отдельный процесс применения версионированных SQL-миграций.

Основной backend является модульным монолитом с границами HTTP → Service → Repository. Demo-ресторан взаимодействует с ним по HTTP и не обращается к его БД.

## Бизнес-сценарии

1. Пользователь просматривает открытые заведения и доступные позиции меню.
2. Backend проверяет цену и остатки, рассчитывает сумму и создаёт заказ одного заведения.
3. Ресторан получает событие заказа и последовательно переводит его в `accepted`, `preparing`, `ready`, `completed`. Также возможен отказ.
4. Пользователь может отменить заказ до принятия рестораном. При отмене или отказе резерв возвращается.
5. Повтор клиентского запроса и повтор события ресторана обрабатываются идемпотентно.

Frontend, платежи, реальная доставка, ETA и курьерский трекинг в проект не входят. Идентификатор пользователя поступает через служебный HTTP-заголовок; пользовательская аутентификация не реализована. Формат заголовка сохранён в OpenAPI для совместимости API.

## REST API

| API | Метод и путь | Назначение |
|---|---|---|
| Client | `GET /api/v1/restaurants` | Открытые заведения |
| Client | `GET /api/v1/restaurants/{id}/menu` | Доступное меню |
| Client | `POST /api/v1/orders` | Создание заказа с `Idempotency-Key` |
| Client | `GET /api/v1/orders/{id}` | Получение собственного заказа |
| Client | `POST /api/v1/orders/{id}/cancel` | Отмена до принятия |
| Partner | `PUT /partner/v1/menu-items/{externalId}` | Создание или обновление позиции |
| Partner | `PATCH /partner/v1/restaurant/status` | Открытие и закрытие заведения |
| Partner | `GET /partner/v1/orders/{id}` | Получение заказа для сверки состояния |
| Partner | `POST /partner/v1/orders/{id}/status` | Идемпотентное изменение статуса |
| Integration | `POST /integration/v1/events` | Приём события demo-рестораном |

Контракты: [основной API](api/openapi.yaml) и [demo-ресторан](api/demo-restaurant.openapi.yaml). Demo operator API позволяет просмотреть полученные заказы и вручную имитировать их обработку.

## Технические решения

**Идемпотентность.** PostgreSQL advisory lock сериализует создание заказа для пары пользователь/ключ. Хэш нормализованного тела позволяет отличить повтор от другого запроса с тем же ключом: повтор возвращает исходный заказ, другое тело получает `409`.

**Транзакции и остатки.** Создание заказа, снимки позиций и цен, резерв, история статуса и запись outbox фиксируются одной транзакцией. Строки меню блокируются через `FOR UPDATE` в стабильном порядке. Это защищает последний остаток от двух параллельных заказов. Отмена и изменение статуса также выполняются в транзакциях.

**Transactional outbox.** HTTP-доставка выполняется после commit. Dispatcher выбирает событие через `FOR UPDATE SKIP LOCKED`, учитывает порядок событий одного заказа и повторяет неуспешную доставку с ограниченным exponential backoff. Lease и номер попытки защищают запись результата от запоздавшего worker. Доставка допускает повторы; demo дедуплицирует события по `event_id`.

**Конкурентность и завершение.** Dispatcher и HTTP-сервер работают в отдельных goroutines. Context используется для отмены, таймаутов HTTP/SQL и graceful shutdown. Состояние demo защищено `RWMutex`, readiness использует atomic. Channels и WaitGroup применяются в конкурентных тестах.

**Границы MVP.** Нет отдельного брокера, Redis или gRPC. Demo теряет своё состояние при рестарте. Общие demo-токены предназначены только для локального стенда; пользовательский ID не является полноценной системой аутентификации.

## Тестирование и CI

- Unit-тесты: переходы статусов, нормализация позиций, неверные количества и retry backoff.
- PostgreSQL integration: два параллельных заказа на последний остаток; восемь повторных запросов с одним idempotency key; повторные partner events, rollback, snapshots, outbox lease и устаревшие workers.
- HTTP E2E: путь заказа через два сервиса и настоящую PostgreSQL, временная недоступность ресторана и последующая доставка события.
- Отдельная проверка мигратора: шесть параллельных вызовов и повторное применение миграций.

GitHub Actions запускается при push и pull request: проверяет форматирование, выполняет `go vet`, тесты с `-race` и coverage profile, сборку, Docker Compose и контейнерный smoke. Конфигурация: [ci.yml](.github/workflows/ci.yml).

Без `TEST_DATABASE_URL` PostgreSQL integration/E2E пропускаются. Используйте отдельную тестовую БД. Команды для самостоятельной проверки:

```bash
go test -p 1 -race ./...
go vet ./...
go build ./...
```

## Запуск

Нужен Docker с Compose v2. Из корня проекта:

```bash
docker compose up --build -d --wait
```

- Основной API: `http://localhost:8080`
- Demo Restaurant API: `http://localhost:8081`
- Readiness: `GET /health/ready`

Мигратор запускается отдельным one-shot контейнером до основного API. Demo синхронизирует меню после readiness основного сервиса. Пример локальных настроек: [.env.example](.env.example).

Сквозной smoke-сценарий:

```bash
docker compose --profile test run --rm smoke
```

Остановка:

```bash
docker compose down
```

## Измерения и происхождение

Сохранённых отчётов RPS, latency и процента покрытия в проекте нет. Количество параллельных запросов выше описывает реализованные тестовые сценарии, а не замер максимальной производительности.

Проект развивался из учебной постановки; оригинальная история коммитов и [исходное задание](backend-trainee-assignment-autumn-2026.md) сохранены. Архитектура, API, схема БД и бизнес-логика не менялись при подготовке этой публикации.
